### Fetch sequence (api-explorer.js, lines ~1775–1816)

```js
Promise.all([
  _aexTryFetchJson([
    '/api/architecture/mcp/registry-summary' + refreshSuffix,
    '/api/architecture/mcp/registry-index' + refreshSuffix
  ]),
  _aexTryFetchJson([
    '/api/architecture/mcp/registry-servers' + refreshSuffix,
    '/api/mcp/servers'
  ]),
  _aexTryFetchJson([
    '/api/architecture/mcp/registry-tools' + toolsSuffix,
    '/api/mcp/tools' + toolsSuffix
  ])
]).then(function (results) {
  var summary = results[0] || {};
  var servers = _aexList(results[1], 'servers');
  var tools = _aexList(results[2], 'tools');

  // Normalize legacy /api/mcp/servers payload if registry endpoint fallback was used
  if (servers.length && !servers[0].id && servers[0].name) {
    servers = servers.map(function (s) {
      return {
        id: s.name,
        service: s.name,
        name: s.name,
        tool_count: s.tool_count != null ? s.tool_count : '-',
        required: !!s.required,
        available: s.available !== false,
        status: s.status || 'configured',
        error: s.error || ''
      };
    });
  }

  _aexRenderMcp(summary, servers, tools, { partial: !!summary.partial });
```

### _aexTryFetchJson behavior (api-explorer.js, lines ~1125–1133)

```js
function _aexTryFetchJson(paths) {
  var i = 0;
  function next(lastErr) {
    if (i >= paths.length) return Promise.reject(lastErr || new Error('no-endpoint'));
    var p = paths[i++];
    return _aexFetchJson(p).catch(next);
  }
  return next();
}
```

This is a **first-success** fetch — it tries each URL in order and returns the first successful response. If all fail, it rejects with the last error. This means:
- For servers: it tries `/api/architecture/mcp/registry-servers` first, then falls back to `/api/mcp/servers`
- The registry endpoint (if available) returns richer data (`id`, `service`, `status`, etc.); the fallback returns the flat config file format

### _aexRenderMcp (api-explorer.js, lines ~1695–1770)

Renders into `#aexMcpServersTbody` (not `#modalMcpServersGrid`). The grid element is populated by a separate function called during modal open. The API Explorer populates a `<tbody>` table, while the Create-Agent modal populates the `tool-grid` div.

## Issues / Corrections Needed

### Issue 1: `registry-*` endpoints return live data, NOT stubs — report was incorrect

The initial report incorrectly claimed that `/api/architecture/mcp/registry-*` endpoints return offline stub data from `_ArchitectureApiGet._architecture_offline_response` (serve.py:15539–15547). This was **wrong**.

**What actually happens:**

In `_architecture_api_get` (serve.py:15549), the `/mcp/registry-*` sub-paths are intercepted **first** (line 15559–15579), before the generic proxy/offline logic is reached:

```python
if sub in {"/mcp/registry-summary", "/mcp/registry-index"}:
    payload = _mcp_registry_snapshot(force=force)
    ...
if sub == "/mcp/registry-servers":
    payload = _mcp_registry_snapshot(force=force)
    self._json_response({"servers": payload["servers"], ...})
    return
if sub == "/mcp/registry-tools":
    payload = _mcp_registry_tools_filtered(force=force, ...)
    return
```

`_mcp_registry_snapshot()` (serve.py:1313) calls `_mcp_server_tools_snapshot()` for each configured server, which spawns the MCP server process and introspects its tools. It returns rich server objects with `id`, `service`, `command`, `args`, `tool_count`, `required`, `available`, `status`, and `error` fields.

`_architecture_offline_response` (the stub function) is only called in the `except Exception` handler (serve.py:15646) when the generic proxy path fails AND the sub-path matches one of the stubbed listing keys. But since the MCP registry paths are handled before that code, the stubs are only a fallback of last resort (e.g., `_mcp_registry_snapshot` itself raises an exception, which would be caught by the try/except around the proxy, not the MCP handler).

**Correction to Issue 1:** The `registry-*` endpoints return live, richly-enriched MCP data. The API Explorer's `_aexTryFetchJson` successfully fetches this data and the normalization branch `if (!servers[0].id && servers[0].name)` at api-explorer.js:1762 will **not** execute for the registry-servers payload (since it has `id`). The fallback `/api/mcp/servers` is only used when the registry endpoint is unreachable.

### Issue 2: `tool_count: '-'` normalization — still valid

This is **not** a bug — it's a minor structural inconsistency between the two consumers. The API Explorer's fallback normalization (api-explorer.js:1774–1786) sets `tool_count: '-'` (string) for servers from `/api/mcp/servers` (which lacks liveness data), while the Create-Agent modal uses `eco.tool_count || 0` from ecosystem enrichment. Since the two code paths render to different DOM targets (table vs. checkboxes) and don't share downstream logic, this is fine. See the Data Flow Summary section for the full picture.

### Issue 3: Token expansion path in `_resolve_mcp_config_path`

When servers contain `${PROJECT_ROOT}` tokens and a server subset is selected, `_resolve_mcp_config_path` (serve.py:573–604) materializes a runtime config copy in `uploads/runtime/`. When no tokens exist and all servers are selected, it returns the original config path. The API Explorer does not trigger this path — it only fetches the server list, not a resolved config file.

### Issue 3: i18n HTML difference

`index-i18n.html` (line 6035) omits the `grid-template-columns:1fr` inline style that `index.html` (line 6412) includes. This means the grid layout may differ between the two pages. Either both should include it or neither should.

### Issue 4: `tool_count: '-'` in API Explorer normalization

When normalizing from the fallback `/api/mcp/servers` payload, the API Explorer sets `tool_count: '-'` (string dash) when the field is absent. The Create-Agent modal uses `eco.tool_count || 0` (number zero). This is a minor inconsistency — the two code paths don't share downstream logic (one renders a table, the other renders checkboxes), so it's not a bug, but it makes the server objects from the two consumers structurally incompatible if ever merged.

### Issue 5: i18n vs. standard HTML `grid-template-columns` — real layout bug (FIXED)

`index.html` (line 6412) applies an inline override `grid-template-columns:1fr` (one column), but `index-i18n.html` (line 6035) omits it.

The `.tool-grid` class in `frontend/css/base.css:1028` defines `grid-template-columns: 1fr 1fr` (two columns). Without the inline override, the i18n page renders MCP server checkboxes in **two columns** instead of one — a visible layout divergence.

**Fix applied:** Added `grid-template-columns:1fr` to `index-i18n.html` line 6035 to match `index.html`. The edit changes:
```html
<div class="tool-grid" id="modalMcpServersGrid" style="margin-top:6px"></div>
```
to:
```html

```
